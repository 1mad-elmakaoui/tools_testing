How this decides

Hard constraints eliminate first. A documented limit or a missing capability removes an option outright; no preference can bring it back. Limits are inclusive, so a payload of exactly 4 MB passes on serverless and 4.000001 MB does not. Setting a p99 target implies the caller waits, because an option that never answers the caller cannot meet a latency target at all.

Soft preferences then rank whatever survived, using weights that are declared alongside the limits with a written rationale. A tie goes to the option with the least always-on infrastructure to run.

If nothing survives, it says so and names the requirements that cannot hold together. It never falls back to a guess.

Every number on this page comes from limits.yaml, the same file the sagemaker-inference-picker CLI reads, and this page is generated from it. A test runs both engines over the same workloads and fails the build if they ever disagree.
